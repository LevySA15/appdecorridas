# Painel do dono — Plano de implementação (plano 4A)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Dar ao Levy um site para tocar o negócio sem usar comandos: aprovar cadastros, ver corridas, dinheiro e taxas, ver devedores, bloquear e liberar pessoas, decidir recursos, resolver alertas de segurança e ajustar os parâmetros, com um registro de tudo o que o administrador fez.

**Architecture:** O painel é uma página única (HTML + JavaScript sem etapa de compilação) servida pelo próprio servidor em `/painel`, que conversa com a API `/v1/admin/*`. O servidor ganha as rotas de leitura que faltam (corridas, passageiros, devedores, dinheiro), as ações que faltam (bloquear e liberar passageiro, ler e gravar parâmetros) e uma tabela `admin_actions` onde cada ação de escrita do administrador fica registrada. Nada de dinheiro novo: o painel só lê o livro-caixa e as contas.

**Tech Stack:** Python 3.12, FastAPI (arquivos estáticos), SQLAlchemy 2 + Alembic, pytest; no navegador, JavaScript puro (`fetch`) e CSS simples. Nenhuma biblioteca nova.

**Spec:** `docs/superpowers/specs/2026-10-08-app-corrida-reconcavo-design.md` (seção 3: "Painel do dono: fila de cadastros para aprovar · lista e detalhe de corridas · motoqueiros e passageiros (bloquear/liberar) · dinheiro e taxas · devedores · alertas de segurança · parâmetros"; seção 13: "site em Python/web, com níveis de acesso desde o início"). Decisões do Levy no roteiro dos planos. Este é o plano 4A, o último da sequência combinada (B, C, D, A).

## Global Constraints

- **Só administrador entra:** todas as rotas novas usam `admin_user` (login por código com `role: "admin"`, como as de hoje). A página `/painel` em si é pública (só HTML e JavaScript, sem dado nenhum); os dados vêm da API, que exige o token.
- **Níveis de acesso:** a spec pede níveis desde o início; este plano grava em cada ação **quem** a fez (`admin_actions.admin_id`) e deixa todos os administradores com o mesmo poder (nível "dono"). Níveis diferentes (por exemplo, "suporte" que só vê) ficam para quando houver mais de uma pessoa (decisão 3).
- **Registro de ações:** toda rota de **escrita** do administrador grava uma linha em `admin_actions` (quem, o quê, em quem, quando, detalhe curto) na mesma transação da ação. Leituras não gravam.
- Dinheiro em centavos inteiros; tempos em segundos (`float`); textos para a pessoa em português do Brasil, simples. Comentários em português; nomes de código em inglês.
- Nenhum serviço faz `commit`; ordem de travas como nos planos 4B a 4D.
- O painel nunca mostra: o conteúdo de `server/.env`, hash de sessão, código de login, `selfie_key`/`cnh_photo_key`/`crlv_key` (os documentos continuam em `/v1/riders/{id}/documents/{kind}`, que já exige login de administrador).
- Os testes usam o Redis banco 15; `systemctl is-active postgresql redis-server` deve responder `active` duas vezes. Comandos a partir de `server/`.
- Commits terminam com `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. Um comando de git por vez.

## Review Focus

1. **Quem não é administrador não lê nem escreve nada:** passageiro, motoqueiro e sem login recebem 403/401 em toda rota nova. Tarefas 1 e 2 (`test_so_administrador_...`).
2. **Toda escrita deixa registro, e só ela:** aprovar, recusar, bloquear, liberar, decidir recurso, resolver alerta, mudar parâmetro; leituras não gravam; ação que falha não deixa registro. Tarefa 2.
3. **Parâmetro inválido nunca é gravado** e o erro chega ao painel em português (preço, taxas, tabela de sem sinal, limites da recarga). Tarefa 2 (`test_parametro_invalido_...`).
4. **Números do dinheiro batem com o livro-caixa:** saldo dos passageiros, dívida dos motoqueiros, pendências de taxa e receita da empresa vêm do banco/livro, não de conta paralela. Tarefa 1 (`test_dinheiro_bate_com_o_livro`).
5. **O site não quebra com dado estranho:** nome com `<script>`, campo vazio, lista vazia, token vencido (volta ao login). Tarefa 3 (escape de HTML testado com `node`, se houver).

## Decisões deste plano (o Levy confere)

1. **Uma página só, sem compilar nada:** `server/painel/index.html` + `painel.js` + `painel.css`, servidos em `/painel`. Troca fácil por outra tecnologia depois, porque toda a regra fica na API.
2. **Login do painel:** telefone do administrador → código (no modo de desenvolvimento o painel oferece um botão "pegar o código" que chama `/v1/dev/otp`) → token guardado só na aba (`sessionStorage`).
3. **Níveis de acesso:** todo administrador é "dono" por enquanto; a coluna `admin_id` das ações já permite mostrar quem fez o quê quando houver mais gente.
4. **Parâmetros:** editados como JSON, uma chave por vez (`pricing`, `fees`, `rides`, `dispatch`, `safety`, `auth`, `balance`), com a validação que o servidor já tem. Uma tela bonita por parâmetro fica para depois.
5. **Mapa ao vivo e gráficos:** fora deste plano (precisam de chave do Google Maps, plano 7). O painel mostra tabelas e totais.
6. **Passageiro bloqueado pelo administrador** usa `users.is_blocked` (já existe e já impede pedir corrida); o motivo fica no registro de ações.
